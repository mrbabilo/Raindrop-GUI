# Audit du dépôt — ouvert le 2026-09-20

Audit fichier par fichier, selon le protocole livré en chat (auditeur senior
Tauri/Node/React). Ce document est **vivant** : il grandit au fil des
fichiers audités. Chaque constat porte son état — `CORRIGÉ` avec le commit,
`OUVERT` avec son entrée ROADMAP, ou `ÉCARTÉ` avec la mesure qui a tué la
piste (les entrées écartées sont la mémoire de l'audit : elles empêchent la
passe suivante de refaire le même chemin).

Méthode : tout test neuf est sabordé avant d'être cru (réintroduire le
défaut, vérifier l'échec, revenir — 12 tests neufs du premier lot, tous
RED vérifiés). Aucune refonte : correctifs localisés aux frontières
naturelles. Interdits respectés : pas de scan de liens en grand, pas de
lancement d'application, baseline sources en lecture seule.

## Cadre, en 10 points (mesuré le 2026-09-20)

1. **Objectif** : GUI macOS (Tauri 2) de diagnostic et réparation pour une
   bibliothèque Raindrop.io Pro de 12 210 signets. Raindrop seule source de
   vérité en écriture ; analyse locale au sidecar (`library_audit` et
   filtres serveur interdits, spec §5.1). Interface en français, textes dans
   `src/i18n/fr.ts`.
2. **Stack confirmée, trois portes** : `npm run build:app` (le gate : vitest
   ×2 + typechecks ×2 + cargo + cliquet de tailles + assemblage .app),
   `npm test` (suite complète : 848 passés / 2 ignorés au 2026-09-20),
   `cargo test` (shell seul). JAMAIS `npm test` et `cargo test`
   concurremment (tests sensibles à la charge, pas instables).
3. **Modules** : front React 18.3 (`src/`, 125 fichiers), sidecar
   Node/Hono (`sidecar/`, 94 fichiers : backup, analysis, trash, jobs/SSE,
   pont MCP épinglé, REST direct), shell Rust (`src-tauri/src/`, 16
   fichiers), scripts Python (build/release/veille).
4. **Livrées** (ROADMAP vérifiée contre `git log`, tête `ecd092f` puis
   lot d'audit) : Phase 1 complète (3 plans) ; sauvegarde (balayage
   12 210/12 210 réel, reprise en vol, archives à budget) ; Nettoyage
   actionnable ; shell poli (en-tête Overlay, thème `system` à chaud,
   reduced-motion) ; mosaïque à plancher 221 px.
5. **Pièges MCP** : erreur tool = TEXTE `Error: ` (jamais un flag) ; 429
   indétectable → file 550 ms, deux rangs ; `domain` ne filtre rien ;
   `POST /raindrops/unrestore` n'existe pas chez Raindrop (sidecar
   l'implémente) ; pagination 50/100 ; `update_raindrop` sans `url` →
   REST direct.
6. **Pièges données** : `cache.size` = stocké (×1,5 décompressé) ; tri
   `created` asc + suppression = saut invisible (seul le `count` décroissant
   le trahit) ; corbeille sans origine (nous notons) ; `/collections` ne
   rend que les racines.
7. **Pièges front** : sentinelle sans garde `isFetchingNextPage` = 5
   requêtes/page (corrigé, `ChargePlus`) ; providers obligatoires en test ;
   route absente du mock = arbre démonté ; accord en nombre français (0 et
   1 → singulier) ; `Object.fromEntries(searchParams)` garde la dernière
   valeur ; chiffres mesurés en dur interdits.
8. **Pièges shell** : `pub fn` non-async = main thread ; PATH sans `node`
   du Finder ; SIGTERM hors `RunEvent::Exit` ; `Child` sans `Drop` =
   zombie ; tarballs nodejs.org (préfixe plateforme, `-C` avant le membre,
   SHASUMS avant).
9. **Méthode** : sabotages obligatoires ; `npm test | tail && git commit`
   commite sur un échec ; pas d'ESLint (`noUnusedLocals` après découpage) ;
   les cases ROADMAP mentent (vérifier `git log`) ; un faux serveur
   infidèle rend le test aveugle (2 occurrences historiques).
10. **Garde-fous** : jamais de scan de liens en grand ; sondes réseau 1-3
    requêtes de métadonnées ; pas de lancement d'app ; DOMAINE.md
    (vocabulaire) et DESIGN.md (apparence) font foi ; corrections §3 de la
    spec primant.

## Audit 1 — `src/components/CleanupView.tsx` et satellites
(`CleanupRows`, `ResultatsLiens`, `EnteteCleanup`, `EtatListe`, `ChargePlus`,
`LigneActivable`, `useAnalysis` partiel, `useMutations` partiel, test voisin)

### 🔴 Bloquants

- **La garde « un exemplaire par groupe » n'était pas structurelle**
  — `find(...)!` sur un ensemble vivant entièrement coché → `TypeError` au
  rendu ; **aucun ErrorBoundary dans `src/`** : écran blanc global.
  La garde ne vivait que dans un `disabled` calculé sur `cochees.size`,
  qui compte des ids peut-être disparus. Chemin réel : un scan lancé
  d'ailleurs achève pendant que la vue est montée avec une sélection
  (`useStartScan` invalide `["analysis"]`, l'invalidation passe outre
  `staleTime: Infinity`, la promesse survit au démontage). **CORRIGÉ**
  (`bb13bd1`) : cochés lus INTERSECTÉS avec le groupe vivant
  (`cocheesDe`), plus aucun `!` — sans gardé désigné, rien ne part.
  Deux tests de garde (gardé disparu, cochés fantômes), sabordés.

### 🟡 Corrigés

- **Suppression individuelle d'une collection vide hors Revue** — le
  DELETE partait au clic sans garde (DOMAINE.md : niveau 2, frappe
  SUPPRIMER). **CORRIGÉ** : op de Revue `delete-collections`, bras
  explicite dans `execute()` (un DELETE par id, `allSettled`, échec
  inline) — l'op inconnue ne retombe plus dans le cleanup global (le RED
  l'a prouvé).
- **NonTaggues hors du patron « ligne activable »** — un arrêt de
  tabulation par case, fiche inatteignable au clavier. **CORRIGÉ** :
  patron complet, le titre est le bouton d'ouverture. Le test a débusqué
  un défaut LATENT de `LigneActivable` : Entrée sur un contrôle interne
  repartait au premier contrôle, le click d'Entrée partait de la case.
  Corrigé au patron (`if (e.target !== e.currentTarget) return`) ;
  `Ligne` accepte désormais les props de sa balise (merge
  onBlur/onKeyDown).
- **CollectionsVides sans état d'erreur** — « Chargement… » éternel en
  cas d'échec (`retry: false`). **CORRIGÉ** : erreur + Réessayer.
- **Parents avec sous-collections listés comme « vides »** — le `count`
  de Raindrop ne voit que les signets directs. **CORRIGÉ** :
  `collectionsVides` (`lib/arbre`) partagé par la vue et le compteur du
  dashboard, ancêtre à tout degré exclu (3 tests). Écart de spécification
  signalé au passage : la spec ne distingue pas suppression unitaire et
  masse — arbitrée en ramenant l'unitaire sous la même Revue L2.
- **Ligne « Remplacer par l'URL finale » ressuscitée à la pagination** —
  le succès ne vivait que dans la ligne (démontée par le paginateur).
  **CORRIGÉ** : le Set des remplacés vit dans la vue (`ResultatsLiens`) ;
  le `total` du chip reste celui du scan, rattrapé au re-scan (même
  contrat que l'élagage des doublons).
- **390 lignes, à dix du plafond** — **CORRIGÉ** : `Doublons` extrait en
  `ResultatsDoublons.tsx` (289 lignes pour CleanupView), tests avec lui ;
  les tests a11y du patron ont rejoint `ResultatsLiens.test`, leur sujet.
  Garde anti-parse et mappers de NonTaggues dédupliqués.

### 🟡 Ouverts (→ ROADMAP)

- 4 erreurs `noUnusedLocals` préexistantes hors lot (imports morts :
  CleanupDashboard/ListPane/Sidebar tests, Signaux.test) — au fil de
  l'eau.
- `refetchOnWindowFocus` (défaut v5, non désactivé dans `main.tsx`) : un
  retour de fenêtre >30 s refetch TOUTES les pages chargées d'une liste
  infinie, à travers la file 550 ms. À trancher à l'audit de `main.tsx`.

### 🔬 Écartés, avec la mesure

- **Chevauchement exact/normalisé dans `triables`** (une même copie deux
  fois en Revue) : écarté — `sidecar/analysis/duplicates.ts:27-31` exclut
  les ids exacts du regroupement normalisé puis du flou ; chaque signet
  vit dans UNE catégorie.
- **Course statut/résultats au premier rendu** (brief « Rien ici » avant
  le statut) : négligeable, le statut léger revient avant des résultats
  passés par la file.
- **`coches` qui gonfle de clés orphelines** : sans effet propre —
  `groupes.find` saute les orphelines ; corriger la garde suffisait.
- **Restauration corbeille sans rafraîchissement** : faux —
  `useUnrestore` invalide `raindrops`/`collections`/`tags`.

## Audit 2 — `src/hooks/useAnalysis.ts`

### 🔴 Bloquants

*(aucun)* L'invalidation `["analysis"]` de fin de scan — racine du chemin
du bloquant 1 — est **correcte en soi** : le résultat doit rattraper les
vues montées, et la promesse du scan doit survivre au démontage du lanceur.
Le défaut était côté vue ; toucher ici aurait cassé le rattrapage voulu.

### 🟡 Ouverts (→ ROADMAP)

- **`useAnalysis.ts:162` — écriture de cache sans lecteur** :
  `["analysis","job",type]` posé à chaque progression, commentaire
  « relisible par T13 » périmé — le dashboard suit par `onEvent` +
  adoption `/api/jobs`. Grep `src/` tout compris : zéro lecteur.
  Retirer la ligne.
- **La clé d'`useAnalysisResults` omet `perPage`** —
  `["analysis","results",type,filter,page]` alors que la requête porte
  `per_page`. Un second appelant à perPage différent lirait le cache de
  l'autre sans erreur. Inclure `perPage` dans la clé, ou supprimer le
  paramètre (mort : tout le monde au défaut 50).
- **Le flux SSE d'un scan survit au démontage sans abort** — le
  `controller` ne sert qu'à l'annulation volontaire (`BlocScan`) ; quitter
  le Nettoyage laisse la connexion ouverte jusqu'à la fin du job (bornée,
  locale ; l'invalidation finale tourne). Un `useEffect` d'abort au
  démontage dans `BlocScan`, ou l'assumer au contrat.
- **Payload complet pour compter les doublons, en deux exemplaires de
  cache** (`["analysis","counts","duplicates"]` + `["analysis","results",
  "duplicates"]`) — dette connue (ROADMAP « à surveiller »), l'élagage
  cible correctement les DEUX clés ; coût borné (414 groupes / 1 032
  signets réels). Remède = compteur dédié sidecar : chantier, pas patch.

### ✅ Ce qui fonctionne

Settle guard R12P-1 (`error` rejette avant `onDone`) ; double invalidation
de fin (`["analysis"]` + `["raindrops"]`) ; `AbortError` d'annulation non
traité en panne ; `useEtatsAnalyse` en `Map` (jamais un tableau contre 12
210 lignes) ; `useCleanupCounts` par la voie la plus légère ; `LinksFilter`
fermé (jamais de chaîne libre au zod) ; `useElaguerDoublons` double-clé avec
bail-out propre sur cache vide ; handle `{jobId, controller}` en state local
de composant, jamais global.

### 🔬 Écartés, avec la mesure

- **`duplicatesCount` afficherait « 1 signets »** (aucun `(s)` sur
  `items`) : impossible — un groupe porte ≥ 2 items par construction
  (`findDuplicates`, et `elaguerGroupes` garde `>= 2`) ; `n=0` implique
  `items=0`, conforme à la règle française.
- **SSE lit après `done`** : le settle guard ignore la suite et le sidecar
  ferme le flux — fenêtre de ms.
- **Buffer résiduel du décodeur perdu à la fermeture** (`sse.ts`) : le
  sidecar termine chaque bloc par `\n\n` — résiduel vide en pratique.
- **`useAnalysisStatus` pollé hors Nettoyage** : faux — seuls
  CleanupDashboard et CleanupView le montent.

## Audit 3 — `sidecar/api/routes/analysis.ts` + `sidecar/analysis/cache.ts`

### 🔴 Bloquants

*(aucun)*. La question croisée du matin — verdict de signet corbellé — a sa
réponse : elle n'est pas un crash, mais un constat d'écran (ci-dessous).

### 🟡 Ouverts (→ ROADMAP)

- **La ligne orpheline est visible ET actionnable vers des actions qui
  échoueront** (`cache.ts:82` + `analysis.ts:105-108`). Choix délibéré du
  2026-09-19 : « un diagnostic orphelin se voit, un diagnostic effacé ne
  se voit pas » — `resultatsParSignet` garde la ligne d'une URL dont plus
  aucun signet connu ne porte (`enrich` : `title = url`,
  `collectionId = -1`). Deux manques : (1) rien ne DIT qu'elle est
  orpheline — `collectionId: -1` entre en **collision de sémantique** avec
  l'identifiant Raindrop des non-classés, et le titre de secours est
  l'URL ; (2) les actions de masse (corbeille, archiver) restent armées
  sur un id qui n'est plus dans la bibliothèque — un trash sur un id en
  corbeille, une archive sans cache. Correction localisée proposée :
  `enrich` porte `orphelin: true` quand la meta manque ; le front écarte
  la ligne de « Tout sélectionner » et le dit. **Non couvert par le
  test** (`analysis.test.ts` ne connaît pas le cas orphelin) — le
  sabordage est à faire à la correction.
- **`POST /scan` étiquette une garde de ré-entrance en `INVALID_INPUT`**
  (`analysis.ts:20`) — `startScan` lève `scan déjà en cours`
  (`scanner.ts:44`) et la route répond 400 INVALID_INPUT. Le message
  affiché à l'écran est clair, le code est trompeur : cosmétique, à
  corriger au passage de l'audit `scanner.ts` (un 409-like).

### ✅ Ce qui fonctionne

`resultatsParSignet` (le piège des 242 signets morts invisibles, corrigé :
le `raindropId` du dernier vérifié est recalculé depuis l'index) ;
`setItemsIndex` REMPLACE avec son contrat écrit et **tenu** —
`scanner.ts:58` sort sur `snap.cancelled` AVANT de peupler l'index ;
`save` atomique (`.tmp` + rename) ; `/etats` avec la précédence voulue
(doublons d'abord, verdict de lien qui écrase — DESIGN §5) et
`resultatsParSignet` et non `allResults` ; filtre des groupes génériques
À LA LECTURE (les caches antérieurs à la règle interstitiel sortent
propres sans re-scan) ; `avancementLiens` lu dans le cache, compté sur
URLs distinctes, et le `>= cutoff` strictement identique à `staleUrls`
(la cohérence maintenue plutôt que rabotée — trap documenté) ;
`per_page` borné (max 200) ; zod fermé sur le filter enum.

### 🔬 Écartés, avec la mesure

- **`Object.fromEntries(searchParams)` à l'entrée de `/results/links`**
  (`analysis.ts:46`) — le trap documenté ne peut pas tirer : les trois
  paramètres (page/per_page/filter) sont des scalaires du protocole, le
  front n'en envoie jamais deux fois (les répétés se perdaient sur
  `?tags=`, route raindrops — corrigée là où c'était réel).
- **Coût de `resultatsParSignet`** reconstruit à chaque requête (~24 k
  opérations sur la vraie bibliothèque) : négligeable à la fréquence
  humaine, y compris `/etats` toutes les 60 s.
- **`getItemsIndex` rend la référence interne** : interne au processus,
  lecture seule en pratique — défensif inutile.
- **`version: 1` sinon cache vidé** (corrompu ou inconnu → vide) : la
  perte coûte un re-scan complet, jamais une donnée (les résultats sont
  refaisables) ; YAGNI assumé sur la rétro-compat.

## Audit 4 — `sidecar/analysis/scanner.ts` + `sidecar/analysis/linkchecker.ts`

### 🔴 Bloquants / 🟡 Ouverts

*(aucun)*. Le carrefour d'analyse sidecar sort propre.

### ✅ Ce qui fonctionne

- **Le dédoublonnage par URL du scan** (`scanner.ts:76-82`) : la leçon des
  11 968 URL distinctes pour 12 210 signets est en code, avec la mesure en
  commentaire — et la progression annonce un total vrai.
- **La chaîne de saves sérialisés** (`scanner.ts:88-93`) : le `.catch`
  consomme le rejet de la promesse retournée, donc pas d'unhandled
  rejection (qui crasherait le sidecar sous Node par défaut) ; le save
  final attend les périodiques déjà en file.
- **`markScanDone` conditionné à l'absence d'annulation** (un scan annulé
  ne rafraîchit pas la fraîcheur du dashboard) ; la reprise par TTL
  (`staleUrls`), trois chemins testés (interruption, relance, TTL expiré).
- **`checkUrl`** : HEAD→GET sur 405/501 ; redirections suivies à la main
  (max 5, `redirect: "manual"`) ; Location malformé → dead (jamais un
  crash du scan) ; boucle → `redirect_loop` ; **401/403/429 →
  `indeterminate`, jamais mort** (DOMAINE.md) ; retry réseau SANS les
  timeouts (coût 2×) ni les statuts HTTP (trap « retry sur les lectures
  seulement » respecté — et le check de liens frappe des serveurs tiers,
  jamais la file Raindrop) ; User-Agent posé.
- **`checkAll`** : pool workers, `isCancelled` par worker (les in-flight
  finissent, les nouveaux targets ne partent plus), `inFlight` décrémenté
  au `finally` (un throw du check ne fuit pas le compteur), annotation du
  raindropId et du `checkedAt` au rendu.

### 🔬 Écartés, avec la mesure

- **La garde `running` du scanner bloquerait pour toujours si `runJob`
  levait synchrone** (`scanner.ts:45` : `running.add` avant `runJob`, le
  retrait ne se fait que par le subscribe du handle) — écarté :
  `store.create` (`store.ts:33`) ne lève pas (uuid + objet littéral, pas
  de garde) ; le chemin est mort. Fragilité théorique notée : si
  `create` gagne un jour une garde de doublon, le scanner se bloquerait —
  la règle serait alors de poser `running.add` APRÈS `runJob`.
- **Après un throw du `check`, les workers continuent de vider la queue
  réseau pour rien** (`checkAll`) : chemin mort en prod — `checkUrl` ne
  lève jamais (`request` capte tout, classification en résultat) ; seul
  un `checkImpl` de test pourrait. `aborted` coupe déjà l'écriture cache.
- **Le retry réseau refait toute la chaîne de redirection** : rare et
  borné (le retry ne part que sur dead-réseau du premier essai).
